# MangoPlayer 项目章程

## 核心原则

### I. 跨平台一致性

**原则**: MangoPlayer 必须在所有支持的平台上提供一致的 API 和行为表现。

**目标平台**:

- **主要支持**: Windows、macOS、iOS、Android
- **未来扩展**: HarmonyOS（待规划实施）

**要求**:

- 所有公共 API 必须在所有主要支持平台上行为一致
- 平台特定实现必须隐藏在统一接口之后
- 功能差异必须明确文档化，并在编译时或运行时明确提示
- 新功能必须同时支持所有主要平台或明确标记为平台特定
- HarmonyOS 支持作为扩展功能，不阻碍主要平台的开发进度

**理由**: Flutter 的核心价值在于真正的跨平台能力。支持桌面端（Windows/macOS）和移动端（iOS/Android）覆盖了主流应用场景，平台差异会增加维护成本和出错风险。

### II. Native 性能优先

**原则**: 播放器性能必须达到或接近各平台原生播放器水平。
- 视频渲染必须保持 ≥30fps（1080p，标准硬件上）
- 内存占用必须与原生播放器相当（误差 ±20%）
- 启动时间必须 <500ms（从初始化到第一帧）
- 使用原生底层库（ijkplayer、ffmpeg、WebRTC 渲染模块）而非纯 Dart 实现
- 所有性能关键路径必须进行 profiling 和优化

**理由**: 音视频播放是性能敏感场景，性能不达标会直接影响用户体验和应用采纳率。

### III. 模块化架构
**原则**: 播放器功能必须模块化设计，便于扩展和测试。
- 核心模块必须职责单一: 播放控制、解码、渲染、缓存等分离
- 模块间通过明确定义的接口通信
- 每个模块必须可独立测试
- 支持功能插件化扩展（如自定义解码器、自定义渲染器）

**理由**: 模块化架构降低耦合度，提高可维护性和可测试性，便于社区贡献和功能扩展。

### IV. 测试优先开发
**原则**: 所有核心功能必须有自动化测试覆盖。
- 单元测试：覆盖所有公共 API 和核心逻辑（目标覆盖率 >80%）
- 集成测试：验证模块间交互和端到端播放流程
- 平台测试：在真实设备/模拟器上验证平台特定功能
- 性能测试：验证关键性能指标（启动时间、帧率、内存占用）
- 回归测试：确保 bug 修复后不再复现

**理由**: 音视频播放涉及复杂的状态管理和异步操作，自动化测试是确保质量和防止回归的关键。

### V. 文档完整性
**原则**: 必须提供完整、清晰的文档支持开发者使用。
- API 文档：所有公共接口必须有详细注释（参数、返回值、异常）
- 集成指南：提供快速开始和完整集成文档
- 示例代码：提供典型使用场景的示例项目
- 架构文档：说明核心架构设计和扩展点
- 更新日志：记录每个版本的变更、破坏性变更和迁移指南

**理由**: 完整的文档降低学习曲线，减少支持成本，提高开发者满意度和采纳率。

### VI. API 稳定性
**原则**: 公共 API 必须保持向后兼容或提供清晰的迁移路径。
- 遵循语义化版本控制（Semantic Versioning）: MAJOR.MINOR.PATCH
  * MAJOR: 不兼容的 API 变更
  * MINOR: 向后兼容的功能新增
  * PATCH: 向后兼容的问题修复
- 废弃的 API 必须保留至少一个 MAJOR 版本，并标记 @deprecated
- 破坏性变更必须在发布说明中明确说明，并提供迁移指南
- 实验性 API 必须明确标记，不受稳定性承诺约束

**理由**: API 稳定性保护现有用户投资，减少升级成本，建立长期信任。

## 技术架构约束

### 核心技术栈
**强制要求**:
- **播放引擎**: 基于 ijkplayer（iOS/Android），FFmpeg + 平台硬解（Windows/macOS）
- **解码器**: ffmpeg（支持主流音视频格式）+ 平台硬件加速（MediaCodec/VideoToolbox/DXVA2）
- **渲染模块**: Flutter External Texture（零拷贝，高性能）
- **插件框架**: Flutter Platform Channels（Method Channel / Event Channel）
- **构建系统**: Dart/Flutter SDK 标准工具链

### 性能基准
**必须满足的性能指标**:
- 启动到第一帧: <500ms (标准网络、720p 视频)
- 渲染帧率: ≥30fps (1080p, 标准硬件)
- 内存占用: <150MB (1080p 播放, 不含缓存)
- Seek 延迟: <200ms (本地文件)
- 电池效率: 与原生播放器相当 (±10%)

### 平台支持
**最低版本要求**:
- **Windows**: Windows 10 (1809+) 及以上
- **macOS**: macOS 10.14 (Mojave) 及以上
- **iOS**: ≥14.0
- **Android**: ≥7.0 (API Level 24)
- **Flutter**: ≥3.0.0
- **Dart**: ≥3.0.0
- **HarmonyOS**: 待定（未来扩展）

**平台优先级**:
1. 核心功能必须在所有主要平台（Win/Mac/iOS/Android）上同时支持
2. 平台特定优化可以分阶段实施
3. HarmonyOS 支持作为独立里程碑规划

## 开发工作流程

### 功能开发流程
1. **需求分析**: 创建功能规范 (spec.md)，明确用户故事和验收标准
2. **技术设计**: 创建实施计划 (plan.md)，定义架构和接口
3. **章程检查**: 验证设计符合所有核心原则（跨平台、性能、模块化等）
4. **测试先行**: 编写测试用例，确保测试失败
5. **实现功能**: 按任务列表 (tasks.md) 实施
6. **测试验证**: 确保所有测试通过，性能指标达标
7. **文档更新**: 更新 API 文档、示例和变更日志
8. **代码审查**: 至少一名核心贡献者审查，验证章程合规性

### 代码审查要点
- 跨平台 API 一致性检查
- 性能影响评估（必要时进行 profiling）
- 测试覆盖率验证
- 文档完整性检查
- 向后兼容性验证

### 质量门禁
**合并要求**:
- 所有自动化测试通过
- 代码覆盖率不低于当前水平
- 无新增编译警告
- 文档已更新
- 代码审查已批准

## 治理

### 章程优先级
本章程优先于所有其他开发实践和文档。所有 PR 和审查必须验证章程合规性。

### 章程修正流程
1. 提出修正提案，说明变更原因和影响范围
2. 核心团队讨论和批准（需多数同意）
3. 更新章程版本号（遵循语义化版本）
4. 更新所有受影响的模板和文档
5. 通知所有贡献者和维护者

### 复杂性证明
如需引入违反简单性原则的复杂设计，必须在实施计划 (plan.md) 中明确证明：
- 为什么需要这种复杂性
- 为什么更简单的替代方案不可行
- 如何最小化复杂性影响

### 运行时指导
开发过程中，使用 `.specify/templates/` 中的模板进行规范化开发：
- `plan-template.md`: 功能实施计划
- `spec-template.md`: 功能规范
- `tasks-template.md`: 任务分解
- `checklist-template.md`: 质量检查清单
